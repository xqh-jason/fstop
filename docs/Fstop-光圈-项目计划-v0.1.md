# Fstop · 光圈 — 项目计划 v0.1

> 项目代号：**Fstop**（中文名：**光圈**）
> 创建日期：2026-09-23

---

## 一、一句话定位

> **Fstop 是一个跑在浏览器里的本地照片检索层。选定一个文件夹，AI 就在你的设备上为照片建立索引，之后你可以用一句自然语言找到任意一张照片——照片不复制、不上传、不需要安装任何服务。**

它不是相册，不是备份工具，是**给已有照片库加的一个「本地的眼睛」**。

## 二、名字的由来

**Fstop（光圈）** —— 相机上控制「有多少光能进来」的部件。

这个产品做的是同一件事的另一面：**决定谁能看见你的光**。光圈只对你打开，照片只留在你这里。

- 英文 `Fstop`：5 个字母、2 个音节，不会拼错，摄影语义明确，不会被误认为通用 AI 工具
- 中文「光圈」：两个字，任何人一看就懂，且自带摄影语境
- 命名可用性：npm 包名 `fstop` 空闲；主流代码托管平台同名仓库均无高热度占用

## 三、问题定义

三个当前无解的场景：

1. 硬盘里存着几万张照片，想找「我妈穿红裙子在西湖的那张」，只能一张张翻。
2. 现有的照片智能检索方案，都要求把照片交给某个服务，或者要求先部署一套服务端、准备显卡。
3. 想给自己的照片库加上 AI 能力，但不愿意为此付出「数据离开设备」的代价。

Fstop 同时解决这三点：**检索能力在本地，数据主权不妥协，使用成本为零。**

## 四、产品边界

### 4.1 要做

- 浏览器内为本地照片建立可检索的索引
- 自然语言语义搜索（跨语言、跨表述）
- 人脸聚类与人物命名
- 相似图 / 重复图分组
- 索引持久化，重复打开不重算
- 完全离线可用

### 4.2 明确不做

| 不做 | 原因 |
|---|---|
| 手机相册自动备份 | 浏览器无法实现，且不是本产品的定位 |
| 多用户 / 分享 / 协作 | 属于服务端职责，会破坏「零部署」的前提 |
| Docker / NAS 部署 | 一旦引入服务端，「零部署 + 零上传 + 零成本」三个前提同时失效 |
| 云端 AI 接口调用 | 与「照片不离开设备」的核心承诺直接冲突 |
| 照片编辑 / 修图 | 与检索定位无关，专注度会被稀释 |

## 六、技术方案

### 6.1 技术选型

| 层 | 选型 | 版本基线 |
|---|---|---|
| 应用框架 | Vue 3 + Vite + TypeScript | Vue 3.5+ / Vite 6+ |
| 推理运行时 | `@huggingface/transformers`（WebGPU 后端） | 4.x |
| 模型执行 | `onnxruntime-web` | 1.30+ |
| 本地数据库 | `@sqlite.org/sqlite-wasm` | 3.53+ |
| 向量检索 | `sqlite-vec` | 0.1.9+ |
| Worker 通信 | `comlink` + 自研任务队列 | 4.x |
| 文件访问 | File System Access API | 浏览器原生 |
| 持久化存储 | OPFS + Cache Storage + IndexedDB | 浏览器原生 |
| 单元测试 | Vitest | 最新 |
| 端到端测试 | Playwright | 最新 |

### 6.2 架构分层

```
┌──────────────── 主线程 ────────────────┐
│  UI 层（Vue）                          │
│    检索框 / 图墙 / 人物页 / 索引进度      │
│                                        │
│  领域层（自己手写，不外包）              │
│    数据模型 · 索引状态机 · Worker 协议   │
└───────────────┬────────────────────────┘
                │ comlink RPC
┌───────────────▼────────────────────────┐
│  Worker 池（并发数 = 核数-1，上限 4）    │
│    embed.worker    CLIP 图像/文本向量    │
│    face.worker     人脸检测 + 特征提取   │
│    ocr.worker      文本识别              │
└───────────────┬────────────────────────┘
                │
┌───────────────▼────────────────────────┐
│  存储层                                 │
│    OPFS      sqlite 数据库 + 向量索引    │
│    OPFS      缩略图缓存                  │
│    Cache     API 模型权重                │
│    IDB       文件夹句柄                  │
└────────────────────────────────────────┘
```

### 6.3 数据模型（SQLite）

| 表 | 关键字段 |
|---|---|
| `roots` | id, handle_key, label, permission_state |
| `photos` | id, root_id, rel_path, size, mtime, taken_at, width, height, thumb_key, embed_status, face_status, ocr_status |
| `embeddings` | photo_id, model_id, dim, vector（BLOB） |
| `faces` | id, photo_id, bbox, cluster_id, vector |
| `clusters` | id, name, cover_face_id |
| `tags` / `photo_tags` | id, name, source |
| `index_runs` | id, root_id, started_at, finished_at, cursor, status |

> 设计原则：**状态全部可查询、可中断、可恢复**。任何一张照片的处理状态都能从 `photos` 表的三个 `*_status` 字段推断出来，索引不允许存在内存态的隐式进度。

### 6.4 Worker 通信协议

```
主 → Worker   { type: 'embed',  jobId, imageHandle, modelId }
              { type: 'cancel', jobId }
Worker → 主   { type: 'progress', jobId, done, total }
              { type: 'result',   jobId, vector }
              { type: 'error',    jobId, code, message }
```

约定：
- 所有消息带 `jobId`，取消与重试都基于它
- Worker 不持有全局状态，一切状态由主线程的索引状态机掌管
- 协议一旦冻结，修改必须走版本号 `protocolVersion`

## 七、性能指标（验收线）

在 M2 MacBook Air / Chrome / WebGPU 环境下：

| 指标 | 目标 |
|---|---|
| 1 万张首次索引耗时 | ≤ 10 分钟 |
| 单张图像向量化 | ≤ 300 ms |
| 语义检索响应 | ≤ 300 ms（1 万张） |
| 冷启动（已建索引） | ≤ 2 秒 |
| 模型首次下载 | ≈ 150 MB，二次打开走本地缓存 |
| 主线程阻塞 | 无任何 > 50 ms 的长任务 |
| 内存峰值 | ≤ 1.5 GB |
| 上传流量 | **恒为 0 字节** |

最后一条是硬性红线：任何功能若需要发出网络请求携带用户数据，直接否决。

## 八、里程碑计划

### M0 · 可行性验证（硬性上限 3 天）

**目标**：证明核心链路成立，不追求任何 UI 质量。

- 单页应用，内置约 20 张样例图
- 跑通：模型加载 → 图像向量化 → 文本向量化 → 余弦相似度排序 → 返回最相似的图
- **决策点**：
  - 单张向量化 ≤ 300 ms → 继续
  - 300 ms ~ 1 s → 降级模型规格后继续
  - > 1 s → 换推理路径（改为手动管理 ONNX 会话）
- **交付**：一个可公开访问的验证页

### M1 · MVP（2–3 周）

**目标**：一个真实可用的最小产品。

- 文件夹选择 + 权限持久化
- 扫描与增量识别（按 mtime + size 判断是否需要重新处理）
- 缩略图墙 + 虚拟滚动
- 语义检索
- 索引进度与断点续算
- **交付**：可对外发布的第一个版本

### M2 · 差异化能力（2–3 周）

- 人脸聚类与人物命名
- 相似图 / 重复图分组
- 检索结果按时间 / 相似度重排
- 离线能力可视化面板（用户可亲眼确认零外发）
- 中英双语界面
- **交付**：具备完整记忆点的版本

### M3 · 发布与传播（1–2 周）

- 静态站点部署，内置样例库，打开即可体验
- 英文优先的 README
- 一篇技术说明：在浏览器里完成检索索引的原理与取舍
- 面向开发者社区的发布节奏
- **交付**：公开版本 + 宣传材料

### M4 · 能力扩张（持续）

| 方向 | 说明 |
|---|---|
| 桌面外壳 | 用 Tauri 补齐「浏览器无法后台处理」的短板，进程管理与本地服务用 Rust 实现 |
| 检索层 SDK | 把索引与检索能力抽成可复用模块，允许接入其它照片来源 |
| 文字识别 | 票据 / 招牌 / 书页内容进入检索范围 |

## 九、技术风险与预案

| 风险 | 影响 | 预案 |
|---|---|---|
| WebGPU 不可用 | 推理慢 5–10 倍 | 运行时能力检测，自动降级 WASM 后端；界面明确提示推荐浏览器 |
| Safari 能力不全 | Mac 用户无法使用 | 对文件访问、OPFS、WebGPU 分别做能力检测；提供明确引导 |
| 文件夹授权过期 | 每次打开都要重新授权 | 句柄存 IndexedDB，启动时查询权限状态，做成「一键恢复」而非报错 |
| 大图解码导致内存暴涨 | 页面崩溃 | 解码即降采样至 224×224；逐张流式处理，不保留原图 |
| 索引过程中断 | 重新计算代价高 | 状态机落盘，以 `index_runs.cursor` 支持断点续算 |
| 模型下载失败 | 产品不可用 | 分块下载 + 断点续传 + 完整性校验 + 支持手动导入 |
| 图库规模继续增长 | 性能衰减 | 向量与缩略图分级存储，检索只读向量，按需加载缩略图 |
| 浏览器存储被清理 | 索引丢失 | 检测 OPFS 可用空间，空间不足时提前告警并降级为轻量模式 |

## 十、工程约定

### 10.1 目录结构

```
fstop/
├── src/
│   ├── app/                应用装配与路由
│   ├── core/               ★ 手写区：数据模型 / 索引状态机 / Worker 协议
│   ├── workers/            推理 Worker
│   ├── storage/            OPFS、sqlite、缓存
│   ├── ui/                 视图与组件
│   └── shared/             工具与类型
├── public/models/          模型清单（不存放权重）
├── docs/                   设计文档
└── tests/                  单元测试与端到端测试
```

### 10.2 三条不可妥协的约定

1. **`src/core/` 手写**。数据模型、索引状态机、Worker 通信协议这三块必须由人设计并逐行确认。其余部分可以借助工具加速，但必须通过类型检查、lint 与单元测试。
2. **任何新增网络请求必须显式声明**。代码中不允许出现隐式的埋点、上报、遥测；引入任何三方脚本都需要单独评审。
3. **`core/` 单测覆盖率 ≥ 80%**。其余模块以端到端测试覆盖关键路径为主。

### 10.3 协作约定

- 提交信息遵循 Conventional Commits
- `main` 分支受保护，功能走 `feature/*`
- 每个里程碑结束打一个 Git tag 并出一份变更说明

## 十一、完成定义（DoD）

一个里程碑被视为完成，必须同时满足：

- [ ] 所有 P0/P1 能力在目标浏览器上手工验证通过
- [ ] 第七章的性能指标全部达标
- [ ] 单元测试与端到端测试通过
- [ ] 断网状态下核心功能完全可用
- [ ] 网络面板确认无任何携带用户数据的请求
- [ ] 文档更新到与实现一致
